# Context

This repository contains a local CLI harness project for learning how Claude Code or Codex style agent runtimes are built.

## Current domain vocabulary

- **Harness**: the runtime layer that coordinates model turns, tools, state transitions, context, policy, and outputs.
- **Provider**: the model backend adapter responsible for normalizing model I/O into runtime-owned structures.
- **Tool**: a runtime-exposed capability the model may invoke through structured calls.
- **Run**: one end-to-end execution of the harness for a user task.
- **Turn**: one model interaction cycle inside a run, including any tool calls and results.
- **Step checklist**: the explicit lightweight step breakdown maintained by the runtime (ordered steps with statuses); injected into the Assembled prompt as progress state, not as the acceptance framing itself. In Plan Mode the checklist is planning-oriented (clarify → read-only explore → write Plan via `update_plan`); after `/execute` it is rebuilt execution-oriented.
  _Avoid_: Plan (for this checklist), Plan Mode, using the execution checklist while still in Plan Mode
- **Plan Mode**: a Session posture that persists across Turns until the user explicitly exits or starts execution; read-only against the workspace; job is to produce a Plan document in Session-scoped honey state. Tool policy is orthogonal to ToolRisk (Approval): offer only a read allowlist plus `update_plan` (v1 read tools: `read_file`, `search_workspace`), omit mutating Tools from the Assembled prompt, and fail closed at dispatch if a mutating call still appears. `exec_command` is never on the allowlist. `update_plan` mutates Session Plan state only, never the workspace. Assembled prompt uses a planning-oriented Step checklist and injects the current Plan document (or an empty marker). Enter with `/plan` (allowed again after `/execute`; re-entry does not auto-rollback the workspace); accept-and-run with `/execute` (leave Plan Mode and promote the current Plan into Task framing for a normal mutating Run; Transcript/Working set soft-continue; Step checklist rebuilt execution-oriented); abandon with `/plan-exit` (leave Plan Mode, keep Plan as draft, do not start execution); `/clear` leaves Plan Mode if active and discards the Plan document along with Transcript, Step checklist, and Working set. Exit is always a user/Harness action, never inferred from model text. Distinct from REPL mode and Command mode (those are entry styles).
  _Avoid_: treating Plan Mode as the Step checklist; half-execute-while-planning; per-Run-only Plan Mode as the primary design; model self-declaring completion as exit; using ToolRisk safe/guarded as a read/write proxy; allowing `exec_command` in Plan Mode; writing Plan into the workspace while still in Plan Mode; deleting Plan on `/plan-exit` by default; auto git-restore on re-entering Plan Mode
- **Plan**: the Markdown specification document produced in Plan Mode. It lives in Session-scoped honey state (outside the workspace cwd), updated via the Tool `update_plan`, and may be shown as a Plan document in the Session TUI. It is not a workspace file by default. Prompting steers a light section shape (Goal, Scope, Approach, Acceptance, Risks / Open questions); v1 stores a non-empty markdown string without strict section schema validation. It is a Root set layer only while Plan Mode is active. On `/execute` its content is promoted into Task acceptance framing for the following mutating Run and it drops out of the Root set; empty Plan rejects `/execute`. Transcript and Working set soft-continue (not cleared); Step checklist is rebuilt for execution; the Plan document remains as a Session archive (still visible in Session state/TUI) but is not re-injected into the Assembled prompt and is not further updated via `update_plan` unless the user re-enters Plan Mode. On `/plan-exit` it likewise leaves the Root set and stays as a draft archive. Distinct from Step checklist.
  _Avoid_: Step checklist, progress state layer, writing Plan into the workspace during Plan Mode, silently equating Plan with Task before `/execute`, treating an archived Plan as still in the Root set after `/execute` or `/plan-exit`, treating chat prose as the Plan without `update_plan`, hard-clearing Transcript on `/execute` as the default, rejecting `update_plan` solely for missing section headings in v1
- **Task**: the current user goal and acceptance framing for the active request; distinct from Step checklist and from an unaccepted Plan. In REPL mode a new user input may continue the current Task or replace it; continuation vs replacement is an explicit Harness decision, not an accidental append.
  _Avoid_: Step checklist goal as a substitute for acceptance framing; unaccepted Plan as a live Task; session-long mission statement; silently stacking unrelated goals into one Task
- **Assembled prompt**: the sole Provider-facing context for a Turn, composed by the Harness from ordered layers rather than from the raw Transcript.
  _Avoid_: full conversation dump, chat history passthrough
- **Transcript**: the durable turn-by-turn message log kept by the Session for continuity and inspection; never sent to the Provider as-is.
  _Avoid_: conversation (when meaning the Provider payload), chat history
- **Environment**: session-scoped facts about the execution setting (for example cwd, platform, or policy summary) injected into the Assembled prompt.
- **Project instructions**: read-only guidance loaded at Session start from `AGENTS.md` only. Discovery uses Instruction sources: user layer is winner-take-all among `~/.honey/AGENTS.md` then fallback `~/.agents/AGENTS.md`; project layer is `<cwd>/AGENTS.md`. When both layers exist, concatenate user then project into the Root set. A single merged char budget applies; if over budget, truncate to preserve the project layer (spill/cut the user layer first). Mid-Session changes to those files are not picked up automatically; `/reload-instructions` re-reads discovery and replaces the Project instructions layer. `CONTEXT.md` remains the domain glossary and is not auto-injected as Project instructions.
  _Avoid_: long-term memory, auto-memory, CLAUDE.md clone as a product feature name; treating CONTEXT.md as Project instructions content; project-then-user merge as the default; concatenating both user roots when `.honey` and `.agents` both exist; naive tail truncation of the merge that drops project before user; per-file-only caps without a merged budget; per-Turn automatic disk reread
- **Instruction source**: a resolved origin of Project instructions content for the current Session — `user` or `project` — always with the concrete file path that won discovery (or none). Distinct from Skill scope.
  _Avoid_: Skill scope, Plugin scope, workspace root
- **Pinned artifact**: an excerpt or instruction fragment retained across Turns and re-injected after Compaction, outside ordinary Working set rotation. It may be established by Harness policy or by an explicit model request, always under Harness quotas.
  _Avoid_: attachment (unless referring to a product-specific injection mechanism), RAG hit
- **Working set**: the recent dialogue and tool I/O layer inside the Assembled prompt for the current Turn.
  _Avoid_: entire Assembled prompt, full Transcript
- **Summary**: compressed prior context retained after history pressure relief, replacing older Transcript material rather than duplicating it. Early writers may be deterministic; later writers may use a model Turn under the same Summary contract.
- **Compaction**: the Harness-owned pressure relief for the Assembled prompt: first clear or shrink re-fetchable tool results under a token budget, then compress older history into Summary when still over budget. Budget checks use a required local token heuristic and may optionally calibrate with Provider-exact counting when available.
  _Avoid_: truncation-only trimming, message-count-only triggers, full Claude Code compaction cascade, provider passthrough history management
- **Root set**: the Compaction-proof layers re-injected every Turn: System, Project instructions, Task, Summary, Step checklist, Plan (only while Plan Mode is active), Environment, Skill catalog, and Pinned artifacts. A Plan document that exists only as a post-`/execute` or `/plan-exit` Session archive is Session state, not a Root set member.
  _Avoid_: full Assembled prompt, Working set, Skill body (loaded via tools into the Working set when used); listing an archived Plan under Root set merely because the document string is non-empty
- **Session**: one interactive terminal conversation started by launching `honey`, preserving Transcript, context layers, Step checklist, and event continuity until the user exits.
- **Session event log**: the Session-scoped durable append-only record of structured HarnessEvents persisted for inspection and replay; distinct from Transcript and from optional Assembled prompt dumps. Streaming deltas are not logged; final assistant content and final Reasoning (when present) are recorded at Turn completion.
  _Avoid_: chat log, conversation dump, prompt dump (as the name of this artifact); per-token / per-delta event spam
- **Context inventory**: the Session-visible breakdown of Assembled prompt layers, token estimates, Compaction status, and Root set membership (aligned with what assembly actually injects — e.g. Plan counts as Root set only in Plan Mode); for Project instructions it also lists the resolved user/project `AGENTS.md` sources and whether merged truncation applied; may also be persisted per Turn as a structural snapshot for later inspection.
  _Avoid_: raw prompt dump as the only observability surface; token-only Project instructions line with no resolved source paths; marking archived Plan as Root set when assembly omits it
- **REPL mode**: the interactive terminal mode entered by running `honey` with no prompt argument, using single-line input and repeated turns.
- **Command mode**: the one-shot CLI mode entered by running `honey "<prompt>"`, executing a single request and exiting.
- **Bin entrypoint**: the packaged executable command exposed as `honey` through npm's `bin` field.
- **Session banner**: the branded welcome surface of a Session (ASCII wordmark plus a short usage line), shown on Session entry and after `clear` in line REPL, and at the top of the Session TUI; never in Command mode.
  _Avoid_: splash screen, startup logo, welcome message
- **Skill**: a reusable task-specific package (instructions plus optional scripts or references) that the Harness may activate for a Task; distinct from Tool (callable capability) and from Project instructions (always-on repo guidance).
  _Avoid_: Tool, Project instructions, prompt template, system prompt fragment (as the name of this package)
- **Skill catalog**: the compact discovery index of available Skills (name, description, path, and optional resource pointers) injected each Turn so the model can see what exists without loading Skill bodies.
  _Avoid_: full Skill body dump, Project instructions
- **Skill picker**: the interactive surface for choosing a Skill (and in the Session TUI, also built-in slash commands). On a TTY this is the `/` overlay in the Session TUI; on non-TTY it lists Skills and directs the user to type `$name`.
  _Avoid_: Skill catalog, full plugin marketplace UI
- **Session TUI**: the Ink-based REPL shell that shows Session banner, Transcript, Status, Composer, and the slash Overlay together; distinct from Command mode and from non-TTY line input. Mid-Turn Draft assistant and Reasoning streaming UX lands here in v1; line REPL and Command mode still present completed Turn output only. The busy `thinking…` spinner stays until the Turn finishes, even while Draft assistant / Reasoning text is already visible.
  _Avoid_: Harness UI, web UI; requiring line REPL / Command mode streaming for v1; clearing the spinner on first content delta
- **Composer**: the Session TUI keystroke-level input box where the user edits the next message and triggers `/` filtering.
  _Avoid_: readline prompt, chat input (as a product name)
- **Reasoning**: model-emitted deliberation content for a Turn, shown separately from the assistant answer. Session-visible for inspection as parallel Session state (not a `ConversationMessage`); never a Working set or Assembled prompt layer. Distinct from the busy spinner placeholder in the Session TUI. When the Provider does not emit Reasoning, only the placeholder (then Draft assistant) appears — the Harness does not invent Reasoning text.
  _Avoid_: thinking (as a name for the busy spinner), fake chain-of-thought, equating Reasoning with assistant answer text; injecting Reasoning into Assembled prompt / Working set; folding Reasoning into Transcript message roles
- **Draft assistant**: the in-progress assistant answer text grown from Provider deltas during a Turn and shown as Session TUI preview only. It becomes a durable Transcript / Working set assistant message only when that model call completes; the preview is discarded after commit. In a tool loop, each model call gets its own Draft assistant. Distinct from Reasoning.
  _Avoid_: treating Draft assistant as already-durable Transcript; appending partial assistant messages per delta; typewriter fake-stream over a finished blob as the product meaning of streaming; streaming only the final model call in a tool loop
- **Skill scope**: the discovery origin of a Skill — repo, user, or bundled — used for precedence when discovering Skills.
  _Avoid_: Plugin scope, Tool risk (as a substitute name for origin); script-approval policy (guarded Skill scripts use Harness Approval)
- **Plugin**: an installable distribution unit that packages one or more Skills (and later may bundle Connectors); not itself a layer in the Assembled prompt.
  _Avoid_: Skill, Tool, Connector (as the runtime configuration surface — that is mcp.json / Harness MCP client)
- **Connector**: a configured external tool provider that contributes Tools to the Harness over MCP (for example an HTTP MCP server entry in mcp.json); discovered Tools merge into the same Tool surface as built-in Tools when MCP is enabled for the Run.
  _Avoid_: MCP server (as the product name for this concept), Plugin, built-in Tool, web_search (as a honey-owned Tool name — web search arrives as Connector-contributed Tools such as Exa's `web_search_exa`)
- **Policy**: the Harness-owned decision surface for Tool authority. It decides which Tools may be offered into the Assembled prompt and whether a given Tool call may proceed at dispatch, evaluating multiple named axes — Session posture (e.g. Plan Mode), **ToolRisk**, **Workspace bound**, and Run-level bypass inputs (e.g. `--allow-guarded-tools` / `--no-workspace-bound`) — and returning a structured multi-axis outcome rather than a single allow/deny boolean. Offer-time returns the filtered Tool list for the Assembled prompt; dispatch-time returns a fully named outcome. Both share one rule core. Dispatch evaluation order matches today's fail-closed sequence and short-circuits: posture / unknown / blocked, then Workspace bound, then needs Approval, then allow (Bound still before Approval). Policy orchestrates; it does not rename or retire those axes. Policy itself does not perform the human pause: when Approval is required, the Harness runs the Approval ritual and then continues or Soft-denies. Dispatch outcomes are fully named (at least: unknown Tool, Plan Mode / posture deny, blocked, Workspace bound reject, needs Approval, allow) so Harness branches on the outcome kind rather than parsing free-text reasons. A subsequent human deny after `needs Approval` is an Approval ritual result (Harness Soft failure + Approval events), not a Policy outcome.
  _Avoid_: collapsing distinct authority axes into one opaque boolean; scattering offer-time and dispatch-time rules in separate ad-hoc filters; treating CLI bypass flags as outside Policy; policy-engine product / OPA-style language as the name of this seam; replacing Approval / Workspace bound / ToolRisk as glossary terms; embedding the Approval host callback inside Policy evaluation; allow/deny/ask-only enums that hide the axis in a reason string; treating Approval deny as a Policy outcome; forcing offer-time through the same per-call authorize outcome path
- **Approval**: the Harness-owned pause before executing a guarded Tool call, where the user allows or denies that specific call and the Turn then continues with the result. It is the human-in-the-loop **ritual** under Policy: Policy decides when Approval is required; the Harness (not Policy) invokes the host callback; Approval is the pause-and-decide moment itself. Scope v1: per-call interactive gate for all guarded Tools via one Harness callback (absorbs the former user Skill-script `confirmSkillScript` special case). Surfaces: Session TUI and line REPL; Command mode stays non-interactive and relies on `--allow-guarded-tools` bypass. When that flag is set, guarded Tools auto-allow and skip Approval. Deny is soft: return a failed Tool result and let the Turn continue (do not abort the Run). The Approval prompt shows the Tool name plus a truncated argument summary (not a full diff/review UI). Approval decisions are first-class Session event log entries (distinct from ordinary `tool_result`), so the pause-and-decide moment is visible on the Session timeline. When a model response contains multiple guarded Tool calls, Approval is sequential: ask and resolve each call in dispatch order before moving to the next.
  _Avoid_: advanced approval workflow, allowlist product; do not conflate Approval with the `--allow-guarded-tools` bypass flag; do not keep a parallel confirmSkillScript path; hard-stop on deny; full-diff Approval UX; folding Approval solely into `tool_result` with no dedicated events; batch-first or fail-fast-batch Approval UI; treating Approval as retired because Policy exists
- **ToolRisk**: the static risk label on a Tool definition — `safe`, `guarded`, or `blocked` — used by Policy as an input axis (whether Approval may be required, or the Tool is refused outright). Distinct from Workspace bound (geometry), Plan Mode (Session posture), and Approval (the human ritual).
  _Avoid_: using ToolRisk as a read/write proxy; conflating ToolRisk with Skill scope or Plugin scope; treating ToolRisk as the whole of Policy
- **Workspace bound**: the Harness-enforced geometric axis that path-taking Tool I/O must resolve under the Session `cwd` (the Environment cwd — not a separately discovered repo root). Bound checks use the real path after symlink resolution, not lexical `resolve` alone. Escape attempts fail without performing the I/O and are recorded as dedicated Session event log entries (distinct from Approval events and from ordinary `tool_result` alone). Applies to path-taking Tools regardless of ToolRisk; under Policy it is evaluated before Approval for guarded path Tools. Default on; may be disabled only via an explicit `--no-workspace-bound` style escape hatch that is orthogonal to `--allow-guarded-tools`. Distinct from Approval and from OS sandbox / command allowlists. Remains a first-class named axis under Policy, not an anonymous deny reason.
  _Avoid_: sandbox, jail, workspace root as an entity separate from cwd; lexical-only path prefix checks; folding Bound into Approval or into `--allow-guarded-tools`; implying shell/`exec_command` is confined by Workspace bound alone; treating Bound as retired because Policy exists
- **Subagent**: a nested Run inside the same Session, started when the parent model invokes the guarded Tool `spawn_subagent` with a `prompt`. It gets a fresh Assembled prompt (own Task and Working set) while inheriting Environment, Project instructions, and Skill catalog; it does not receive the parent Transcript or Working set. Depth is fixed at one: a Subagent cannot call `spawn_subagent`. Guarded Tools inside the Subagent use the same Session Approval callback as the parent. Parent Session TUI does not stream the Subagent’s Draft assistant / Reasoning; the parent sees the Subagent result. Distinct from a new Session and from swapping roles inside one Assembled prompt.
  _Avoid_: Agent (as a peer entity beside Harness), child session, worker, multi-agent orchestration DAG; nesting Subagent streaming into the parent Transcript for v1
- **Subagent result**: the structured Tool result returned to the parent after a Subagent finishes — at least `summary`, `status`, and `run_id`, with a hard character cap on `summary`. It is not the Subagent Transcript; full nested detail lives in the Session event log under the Subagent `run_id` (linked via `parent_run_id`).
  _Avoid_: full child Transcript dump into the parent Working set
- **Soft failure**: a Tool or policy outcome delivered into the Working set as a failed Tool result so the Run can continue; the model may change parameters, switch Tools, or re-probe on later Turns. Covers Tool execution failures, Approval deny, Workspace bound rejection, unavailable/unsupported Tool or Connector outcomes, and Environment mismatches reported through Tool results. Does not cover a successful Tool result that simply fails Task acceptance. v1 formats Harness-dispatch Soft failures as actionable free-text (what failed, why, what to try) plus light System guidance; built-in Tool and Connector message polish is follow-up — not a structured recovery schema.
  _Avoid_: exception-as-abort, Harness auto-remediation, treating Task-miss as a Soft failure, recovery error codes as the v1 contract
- **Hard failure**: a condition that ends the Run in ERROR because another Turn cannot usefully proceed — for example Provider/transport failure, illegal stop reason, or hard budget exhaustion.
  _Avoid_: Soft failure; treating Soft failure Tool results as Run-ending errors

This glossary is intentionally small and should grow only when a term becomes stable and necessary.
