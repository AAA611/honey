# 上下文管理实现原理解析

**问题：** 对话和工具结果越积越长时，如何既不把整段聊天原样塞给模型，又不在减压时丢掉目标与关键材料？

**契约：** Provider（模型后端适配）每轮只看见 Harness（运行时协调层）现场组装的 **Assembled prompt**；Session 的 **Transcript** 只做连续性与观测，从不原样下发。超预算时 **Compaction** 先腾可再取的工具结果，再把更早对话压进 **Summary**；**Root set** 每轮回注，Working set 可被改瘦。

**读者：** 有通用编程基础、第一次接触 honey 上下文子系统的人。读完应能不翻仓库讲清：本轮模型实际看到什么、超预算时谁先被砍、谁必须留下；并对下列函数口述「进去之后先判断什么、改了什么、从哪返回」。

权威决策见 [ADR-0003](../docs/adr/0003-context-engineering-architecture.md)；术语以根目录 [`CONTEXT.md`](../CONTEXT.md) 为准。ADR 早期把 Step checklist 称作 Plan，读代码时以 CONTEXT 为准。

**Unpack（概念）：** Assembled / Transcript / Working set / Root set 的分工；Compaction 两级减压与 pair-safe 切分；一回合里何时写层、何时 compact、何时 `sendTurn`。

**Dissect（实现）：** `compactIfNeeded`（含清工具结果、`summarizeOverflow`、`findPairSafeSplit`）；`assembleSystemPrompt` / `assembleProviderMessages` / `estimateAssembledTokens`；`runTurnLoop` 主循环与 `appendMessages` 双写。

## 1. 要解决什么

编码 Agent 的上下文会同时变长、变脏、变贵：

- 工具结果（读文件、搜仓库）体积大，多数可再取；
- 目标、进度、仓库规范若跟着「随便截断」一起丢，下一轮会失忆；
- 若把整段 Transcript 透传给 Provider，分层装配与减压都成摆设。

honey 的非目标（ADR-0003）：不做 Claude Code 全套 cascade；不做可写长期记忆；不用「消息条数」当主压力信号。

答案形状：**Harness 拥有装配与减压** —— 分层原料 → 估 token → 必要时 Compaction → 再发给 Provider。

## 2. 核心契约

先建立一张「两份账本」心智图：

```text
Session
├── Transcript          ← 完整日志账本（给人看 / 可观测；不直接发 Provider）
└── ContextLayers       ← 装配原料账本
    ├── Root 侧字段     → 拼进 systemPrompt（减压后仍每轮回注）
    └── workingSet      → 拷贝成 messages（可被清结果 / 压进 Summary）

每 Turn 唯一下发：
  Assembled prompt = systemPrompt(Root 拼段) + messages(Working set 拷贝)
```

| 概念 | 含义 |
|------|------|
| **Assembled prompt** | 本 Turn 唯一的 Provider 输入：`systemPrompt` + `messages` |
| **Transcript** | Session 持久的轮次日志；与 Working set 同步追加，但不作为 Provider payload |
| **ContextLayers** | 装配用的分层状态（system / task / workingSet / summary / pinned …） |
| **Root set** | Compaction 后仍每轮回注：System、Project instructions、Task、Summary、Step checklist、Plan（仅 Plan Mode）、Environment、Skill catalog、Pinned |
| **Working set** | Assembled 里「最近对话 + 工具 I/O」；可被清结果 / 压进 Summary |
| **Compaction** | 超 `tokenBudget` 时两级减压：① 清/缩可再取工具结果 ② 仍超则把更早消息写成 Summary |
| **Context inventory** | `/context` 展示的层 token 估计与 Compaction 状态；可另有 per-Turn `AssemblySnapshot` |

**Example（两份账本不同步变瘦）：** Compaction 把 Working set 里某次 `read_file` 大结果换成 `[cleared refetchable …]` 后，Assembled 变短；Transcript 仍保留当时写入的完整 tool 消息。Session 观测与 Provider 预算由此解耦。

## 3. 概念地图：零件怎么协作

不要按目录想，按「谁喂原料、谁减压、谁拼成 Provider 输入」想：

```text
用户输入
  │
  ├─► Task transition / pin / $skill     （改 ContextLayers 的 Root 侧字段）
  ├─► 用户消息 ──► Transcript（追加）
  │              └──► Working set（追加）
  │
  ▼
Compaction（估 token → 必要时改 Working set / Summary）
  │
  ▼
装配
  ├─ Root 侧字段 + checklist + Plan(Mode)  →  systemPrompt
  └─ Working set 浅拷贝                    →  messages
  │
  ▼
Provider.sendTurn(Assembled prompt)
  │
  ├─ assistant / tool 消息 ──► Working set（+ 有则 Transcript）
  └─ 工具写入后再 compact 一次
```

协作关系一句话：**ContextLayers 是可变原料；Assembled prompt 是每轮现场烤出来的成品；Transcript 是旁路档案，不进烤箱。**

脚注（核对用）：原料与装配在 `src/context/`；Session 入口与循环在 `src/runtime/harness.ts`、`turnLoop.ts`。

## 4. 端到端链路

一次用户发言走完：

```mermaid
sequenceDiagram
  participant User as User / REPL
  participant Sess as HarnessSession
  participant Loop as runTurnLoop
  participant Compact as compactIfNeeded
  participant Asm as assemble*
  participant Prov as Provider

  User->>Sess: runTurn(input)
  Sess->>Sess: Task transition / pin / skillInstructions
  Sess->>Sess: transcript += user; workingSet += user
  Sess->>Compact: compactIfNeeded（进循环前一次）
  Sess->>Loop: TurnLoopScope
  loop each model turn
    Loop->>Compact: compact before send
    Loop->>Asm: systemPrompt + messages
    Loop->>Prov: sendTurn(Assembled prompt)
    alt tool_calls
      Loop->>Loop: executeTool → append tool msgs
      Loop->>Compact: compact after tools
    else completed
      Loop-->>Sess: DONE
    end
  end
```

进循环前，`HarnessSession.runTurn` 依次：`decideTaskTransition` → 解析 `$skill` → `autoPinFromUserInput` → 用户消息写入 Transcript **与** Working set → `compactIfNeeded` 一次 → 交给 `runTurnLoop`。

Subagent 用新的 `ContextLayers`（新 Task + 空 Working set），继承 Project instructions / Environment / catalog，**不**带父 Transcript——隔离靠新 layers，不是靠提示词「请忽略上文」。

## 5. 边界与易混点

| 对照 | 是 | 不是 |
|------|----|------|
| Transcript vs Assembled | 同 Session 可查日志；与 Working set 并行追加 | Provider 的 `messages` |
| Root set vs Working set | 减压后仍每轮进 system 拼段 | 可被清工具结果 / 整段压进 Summary 的近期 I/O |
| Task vs Step checklist vs Plan | Task=验收框；checklist=进度层；Plan=Plan Mode 下的 Markdown 规格 | 三者互相顶替 |
| Project instructions vs CONTEXT.md | 只注入发现到的 `AGENTS.md` | 领域词表 `CONTEXT.md` 不自动进 prompt |
| Skill catalog vs skillInstructions | catalog 每轮 Root；`$name` 体进本 Run 的 `skillInstructions` | 把全部 Skill 正文当 catalog |
| Pinned vs Working set 里的读文件结果 | pin 跨 Compaction 回注 | 普通 `read_file` 结果可被清掉再读 |

**Example（父有、子不见）：** 父 Working set 里已有大段 `search_workspace` 结果；`spawn_subagent` 子 Run 的 Assembled 只有 spawn 的 `prompt` 作 Task/用户句，看不到父 Working set。

## 6. 机制深挖

概念零件之后，对着真码拆三个入口。

### 6.1 Compaction：概念零件

压力信号是「若现在 assemble，估出来的 token」相对 `tokenBudget`，不是消息条数。热路径用本地启发式 `ceil(len/4)+1`（`estimateTokens`）；Provider 精确计数不作热路径依赖（ADR-0003）。

两级能停就停：

```text
estimate ≤ budget? ──yes──► 原样返回
        │ no
        ▼
清/缩 refetchable 大工具结果 → 再估；够了就返回（clearedTools）
        │ 仍超
        ▼
pair-safe 切走 Working set 头部 → SummaryWriter → summary[]
必要时再把残留 tool 压到更短（summarized）
```

| 零件 | 是什么 / 做什么 | 如何接上 |
|------|-----------------|----------|
| `estimateAssembledTokens` | 估「现在拼出来」的体积 | 每级前后的闸门 |
| `clearRefetchableToolResults` | 可再读且超长 → 占位；不可再读 → 硬截断 | 第一刀，只改 tool 消息 |
| `summarizeOverflow` | 切走头部，写入 `summary[]` | 第二刀；Summary 仍在 Root |
| `findPairSafeSplit` | 剩余序列不以孤立 `tool` 开头 | 切点合法性 |
| `deterministicSummaryWriter` | 溢出消息压成一行短串 | 可替换的 `SummaryWriter` |

### 6.2 Dissect：`compactIfNeeded`

**何时被叫：** `HarnessSession` 写入用户句之后进循环前一次；`runTurnLoop` 每次 `sendTurn` **之前**，以及工具结果写入 Working set **之后**，各一次。调用方传入当前 `ContextLayers`、`stepChecklist`、`tokenBudget`、可再读工具名集合，以及 Plan Mode 相关的 assemble 选项（估 token 时要算进 Plan 节）。

**主路径逐步：**

1. 构造 `estimateOpts`（checklist + planDocument + planMode）。
2. **浅拷贝** `workingSet` / `summary` / `pinned` / `compaction`，得到可变的 `next`——不原地改调用方手里的对象。
3. 若 `estimateAssembledTokens(next) ≤ tokenBudget` → **直接返回**拷贝（未减压）。
4. 否则调用 `clearRefetchableToolResults`，并把 `compaction.clearedTools = true`（哪怕实际几乎没清到字，标志也会置位）。
5. 再估一次；够了 → 返回（只做了第一刀）。
6. 仍超 → `return summarizeOverflow(...)`（第二刀；该函数会把 `summarized` 也置 true）。

```89:103:src/context/compact.ts
  if (estimateAssembledTokens(next, estimateOpts) <= tokenBudget) {
    return next;
  }

  // 第一刀：腾可再读的工具结果（丢了还能再调工具拿回来）
  next = clearRefetchableToolResults(next, refetchableTools);
  next.compaction = { ...next.compaction, clearedTools: true };

  if (estimateAssembledTokens(next, estimateOpts) <= tokenBudget) {
    return next;
  }

  // 第二刀：仍超 → 把 Working set 头部压进 Summary
  return summarizeOverflow(next, estimateOpts, tokenBudget, summaryWriter);
```

**状态怎么变：** 返回新的 `ContextLayers`。可能变的是 `workingSet` 里 tool 的 `content`、`summary` 数组、`compaction` 两个布尔；`task` / `pinned` / `projectInstructions` 等 Root 侧字段不被这一步删除。

#### 第一刀：`clearRefetchableToolResults`

对 `workingSet` 逐条 `map`：

- `role !== "tool"` → 原样；
- 工具名**不在** `refetchableTools` → `shrinkToolContent`：超过 800 字则硬截断到 800；
- 在集合内且 `content.length ≤ 800` → 原样留下；
- 在集合内且更长 → 换成占位串 + 原文前 120 字：`[cleared refetchable ${toolName} result; re-read if needed] …`。

内置可再读集合：`read_file` / `search_workspace` / `run_tests`；Connector 若标记 `definition.refetchable`，由调用方并进 `refetchableTools`。

#### 第二刀：`summarizeOverflow` + `findPairSafeSplit`

外层 `while` 条件：`workingSet.length > 2` **且** 估 token 仍超预算。循环体内：

1. `splitAt = findPairSafeSplit(workingSet)`；若 `≤ 0` → **break**（切不动）。
2. `overflow = slice(0, splitAt)`，`workingSet = slice(splitAt)`。
3. `summary.push(summaryWriter.write(overflow))`。

切完仍超预算时，还有第二段 `while`：只要还有 `role === "tool"` 且 `content.length > 160`，就把这些 tool 内容截到 160——最后手段，不再切消息边界。

返回时固定：

```199:207:src/context/compact.ts
  return {
    ...layers,
    workingSet,
    summary,
    compaction: {
      clearedTools: true,
      summarized: true
    }
  };
```

`findPairSafeSplit` 的控制流：

1. `length ≤ 2` → 返回 `0`（太短不切，留给外层 break）。
2. `maxSplit = length - 2`（至少留两条在 Working set）。
3. 从 `maxSplit` 往下扫到 `1`：若 `workingSet[index].role === "tool"` 则 **跳过**（否则 `slice(index)` 会以孤立 tool 开头）；否则 **返回该 index**。
4. 扫完没有合法点 → `0`。

**Example（同一组消息跑进函数）：**

```text
Working set:
[0] user: 找入口
[1] assistant: 我来搜
[2] tool: search_workspace → 很长结果（>800）
[3] user: 再读 src/main.ts
[4] assistant: 正在读
[5] tool: read_file → 很长结果（>800）
```

假设估 token 远超预算：

1. `compactIfNeeded` 过闸门 → 第一刀：两条 tool 都变成 `[cleared refetchable …]` 占位；若仍超预算进入第二刀。
2. `findPairSafeSplit`：`length=6`，`maxSplit=4`；下标 4 是 `assistant`（非 tool）→ 返回 `4`。
3. 切走 `[0..3]` 写成一行 Summary；Working set 剩 `[4][5]`（assistant + tool）。
4. 若仍超且 tool 内容 >160，再截到 160；`compaction = { clearedTools: true, summarized: true }`。

切点**不会**选在 `2` 之后立刻留下以 `tool` 开头的尾巴：候选下标若是 tool 会被 `continue` 掉。

**为何 Transcript 不变瘦？** Compaction 只返回新的 `ContextLayers`；没有任何路径把瘦身后的 Working set 回写进 Transcript。双写只发生在追加时（见 6.4），追加之后的 compact 只动装配原料。

### 6.3 Dissect：装配三函数

**何时被叫：** `runTurnLoop` 在本轮 `compactContext` 之后、`provider.sendTurn` 之前；`estimateAssembledTokens` 还被 `compactIfNeeded` 与 Context inventory 用作闸门/展示。

**`assembleSystemPrompt` 主路径：**

1. `resolveAssembleOptions`：兼容「只传 Step checklist」的旧形；规范化出 `stepChecklist` / `planDocument` / `planMode`。
2. 按固定顺序建 `sections` 数组：裸 `layers.system`；若 `planMode` 则插入 Plan Mode 说明节；其余用 `section(title, body)`——`body` trim 后为空则该节变成 `""`。
3. Plan 节：仅当 `planMode` 为真才有内容；有文档用文档，否则用空标记 `(empty — call update_plan …)`；非 Plan Mode 时 Plan 节为空串。
4. `Summary` 节：`layers.summary.join("\n")`；Pinned 用 `## label` + content。
5. `sections.filter(Boolean).join("\n\n")` —— 空节不占位。

```23:54:src/context/assemble.ts
  const sections = [
    layers.system,
    resolved.planMode

  ];

  return sections.filter(Boolean).join("\n\n");
```

**`assembleProviderMessages`：** 对 `workingSet` 做 `map` 浅拷贝每条消息——**不读 Transcript**，不合并 Root 字段。这是契约「Transcript 从不原样下发」在代码里的落点。

**`estimateAssembledTokens`：** `estimateTokens(assembleSystemPrompt(...))` + Working set 每条 `estimateMessageTokens`（内容启发式 + 可选 toolName 税 + 常数 4）之和。Compaction 与装配共用同一估法，避免「压的时候一套尺、发的时候另一套尺」。

**Example：** `planMode=false`、`summary=["user:找入口 | tool:search_workspace:ok:…"]`、`workingSet` 仅剩最近两条时——system 侧仍有 Task / Summary / Pinned 等非空节；`messages` 只有那两条 Working set 拷贝。Provider 看不到已被切进 Summary 之前的原文 tool 大段（除非 Summary 行里还留着 80 字截断痕迹）。

### 6.4 Dissect：`runTurnLoop` 与双写

**何时被叫：** 父 Run 由 `HarnessSession.runTurn` 在预热（Task / pin / 用户句 / 进循环前 compact）之后调用；Subagent 在自己建好 layers 后调用同一函数。

**循环内主路径（每个 model turn）：**

1. 状态 → `MODEL_TURN`。
2. `scope.context = compactContext(scope)` → 内部就是 `compactIfNeeded(...)`（发前减压）。
3. `assembleSystemPrompt` + `assembleProviderMessages`；可选 `createAssemblySnapshot` / prompt dump；打 `model_request` 事件。
4. `provider.sendTurn({ systemPrompt, messages, tools })`。
5. 若有 `assistantMessage` → `appendMessages`。
6. `stopReason === "completed"` → 标 checklist、DONE、break。
7. `stopReason !== "tool_calls"` → ERROR、break。
8. 否则：执行每个 tool → 收集 tool 消息 → `appendMessages` → **再次** `compactContext` → 状态 `TOOL_RESULT`，进入下一轮循环（下一轮开头还会再 compact 一次再发送）。

```67:104:src/runtime/turnLoop.ts
    const assembleOpts = assembleOptions(scope);
    const assembledSystem = assembleSystemPrompt(scope.context, assembleOpts);
    const assembledMessages = assembleProviderMessages(scope.context);
    // ... snapshot / dump / model_request ...
    let response;
    try {
      response = await scope.provider.sendTurn({
        systemPrompt: assembledSystem,
        messages: assembledMessages,
        tools: scope.tools
      });
```

**`appendMessages` 状态变化：**

```191:198:src/runtime/turnLoop.ts
function appendMessages(
  scope: TurnLoopScope,
  messages: ConversationMessage[]
): void {
  scope.context = appendWorkingMessages(scope.context, messages);
  if (scope.transcript) {
    scope.transcript.push(...messages);
  }
}
```

- Working set：不可变更新（`appendWorkingMessages` 展开旧数组再拼接）。
- Transcript：若 scope 带了 `transcript`（父 Run 会带），**原地 push** 同一批消息。
- Subagent 的 scope 通常**不**传 `transcript`，因此子 Run 的 assistant/tool 不会污染父 Transcript；父只通过 Subagent result 工具结果看到摘要。

**与进循环前的衔接：** `runTurn` 里用户句已经双写并 compact 过一次；循环第一次迭代开头的 compact 多半是 no-op（除非并发逻辑改过 layers——当前路径上主要是幂等再估）。真正「工具结果把预算撑爆」的减压，发生在工具后的那次 `compactContext`，以及下一轮发送前的再估。

**Example（同一次 `read_file`）：**

1. 工具返回 → `appendMessages`：Transcript 与 Working set 都有完整结果。
2. 紧接着 `compactContext`：若超预算，Working set 里的结果可能被占位/截断；Transcript 仍是全文。
3. 下一轮 `sendTurn` 的 `messages` 来自瘦后的 Working set；模型若还需要文件，应再调 `read_file`。

### 6.5 周边机制（轻量）

这些支撑契约，但不在本文 dissect 主名单上——只钉行为边界：

- **Pinned：** `autoPinFromUserInput` 扫 `@path` / 裸路径，最多 4 条、单条约 1200 字，进 Root 的 Pinned 节，跨 Compaction 回注。
- **Project instructions：** Session 构造时加载 `AGENTS.md`（user 胜出链 + project）；合并超预算先砍 user、保 project；`CONTEXT.md` 不自动注入。
- **Task transition：** `/new` → replace；续写 cue → continue；checklist 全 done 且新句像新目标 → replace；默认 soft-continue。
- **可观测：** `/context` → inventory；每 Turn `AssemblySnapshot`；可选 Assembled 全文 dump。

## 7. 为何不是别的形状

| 备选 | 否决理由（ADR-0003） |
|------|----------------------|
| Transcript 透传 + 装饰性 layer | Working set / Summary 不生效 |
| 全套 Claude Code cascade | 学习价值在自管预算与两级减压，不在复刻生产梯队 |
| 仅按消息条数裁剪 | 教不出 token 预算下的 context rot |
| 可写长期记忆 | 与 v0 范围冲突；稳定跨轮指导用只读 Project instructions |
